# 발표 자료 — 평가(Evaluation) 파트 · 8조

> 대전 독거노인 복지 RAG 상담 + 이상신호 감지 시스템
> PPT 에 붙여넣기 쉽게 **슬라이드별 내용 + 🎤 대본 + 예상 질문** 으로 정리.

---

## 슬라이드 1 — 왜 평가가 필요한가

**내용**
- "잘 된다"는 느낌이 아니라 **숫자로 증명**해야 함
- 교수님 피드백: *"정답지(ground truth)를 만들어 정량 평가하라"*
- 우리 시스템은 2가지 → 평가도 2가지
  - RAG 복지 상담 (검색 + 생성)
  - 이상신호 감지 (정상/주의/위험)

🎤 **대본**
"저희는 시스템 성능을 느낌이 아니라 수치로 보여드리기 위해, 사람이 정한 정답지를 직접 구축하고 정량 평가했습니다."

---

## 슬라이드 2 — 정답지(Ground Truth) 구축

**내용**
- `ground_truth_rag.jsonl` — **질문 200개** (복지 10주제 × 15 + 범위 밖 50)
  - 각 질문: 정답 주제 · 검색 키워드 · **핵심 정답** · 정답 인정 용어 · scope
- `ground_truth_signal.jsonl` — **대화 19개** (정상 7 / 주의 7 / 위험 5)
- **공식 문서(보건복지부 PDF 등) 기반**으로 지정, **팀원이 검토·승인**
- JSONL 이라 누구나 열어 보고 고칠 수 있음 (재현·검증 가능)

🎤 **대본**
"정답은 공식 문서를 근거로 정하고, 한국어 팀원이 공식 자료와 대조해 검토·승인했습니다. 자동 생성이 아니라 사람이 검증한 정답지입니다."

---

## 슬라이드 3 — 평가 방법 (지표)

**내용**
| 축 | 지표 | 의미 |
|---|---|---|
| 검색 | **Hit@1 / Hit@3** | 정답 근거가 상위 1·3개에 오나 |
| 검색 | **Context Precision / Recall** | 노이즈 적나 / 정답 근거 누락 없나 |
| 생성 | **Faithfulness** | 근거에만 기반하나 (환각 없음) |
| 생성 | **Answer Relevance** | 질문에 제대로 답하나 |
| 거절 | **범위 밖 거절률** | 무관한 질문을 지어내지 않고 거절 |

- **RAGAS 방식**의 4대 지표를 **직접 구현** (라이브러리 미사용)
- 심판·생성 모두 **로컬 EXAONE** → **완전 on-device** (외부 API 없음, 프라이버시)

🎤 **대본**
"검색은 Hit@k, 생성은 RAGAS 방식 4대 지표로 평가했습니다. 모든 판정을 로컬 LLM으로 수행해 대화 내용이 외부로 나가지 않습니다."

## 슬라이드 4 — 평가로 약점을 찾다 (핵심)

**내용**
- 초기 전체 **Hit@3 = 51%** — 일부 주제가 매우 낮음
- 검색 실패 조각을 직접 분석(디버그)해 **원인 3가지**로 분리:
  1. **코퍼스 공백** — 기초연금·에너지바우처·정신건강 제도가 문서에 없음
  2. **명단 노이즈** — 경로당·시설 현황 스프레드시트가 검색을 오염
  3. **측정 과엄격** — 관련 조각은 왔으나 키워드 불일치(치매)

🎤 **대본**
"낮은 수치를 그냥 넘기지 않고, 실제 검색 결과를 열어 원인을 세 가지로 나눴습니다. 평가가 약점을 구체적으로 짚어준 것입니다."

---

## 슬라이드 5 — 개선 (평가 기반 개발)

**내용**
- **① 측정 교정** — 치매 키워드 완화(공식 조각은 실재)
- **② 노이즈 제거** — 명단 현황 스프레드시트 색인 제외
- **③ 공식 문서 보강** — 보건복지부 **기초연금·자살예방사업 안내**, **에너지바우처** 공식 PDF 추가
  - ⚠️ 자가작성 요약은 **철회** → **공식 출처만** 사용 (평가 무결성 유지)

🎤 **대본**
"원인별로 측정을 바로잡고, 노이즈를 제거하고, 부족한 주제는 공식 문서를 추가했습니다. 특히 AI가 쓴 요약은 넣지 않고 공식 출처만 사용해 평가 신뢰성을 지켰습니다."

---

## 슬라이드 6 — 결과 (개선 전/후)

**내용**
| 지표 | Baseline | **최종** |
|---|---|---|
| **전체 Hit@3** | 51% | **75%** (+24%p) |
| 전체 Hit@1 | 38% | **63%** |
| 기초연금 | 33% | **93%** |
| 정신건강 | ~20% | **93%** |
| 에너지바우처 | 0% | **73%** |
| 범위 밖 거절 | — | **98%** |

- **생성 품질:** Faithfulness **95%** (환각 거의 없음), Answer Relevance ~85%
- **이상신호(LLM 심판):** 3단계 정확도 **89%**, 이상 여부 F1 **1.00**, **위험 Recall 60%**

🎤 **대본**
"그 결과 전체 Hit@3 가 51%에서 75%로 올랐고, 핵심 복지는 90% 이상을 달성했습니다. 생성은 Faithfulness 95%로 환각을 잘 억제했고, 위험 신호도 놓치지 않도록 설계했습니다."

## 슬라이드 7 — 한계 & 향후 과제 (정직하게)

**내용**
- 방문건강관리(27%)·노인맞춤돌봄(40%) — 해당 공식 문서 추가 보강 여지
- 심판을 답변 모델과 같은 로컬 LLM 사용 → 교차검증(다른 모델) 보완 가능
- 정답지 규모 확대(200→더) 시 통계적 신뢰도 ↑

🎤 **대본**
"일부 주제는 아직 보강이 필요하고, 심판 모델 교차검증 등은 향후 과제입니다. 한계도 수치로 정직하게 드러냈습니다."

---

## 슬라이드 8 — 핵심 메시지

**내용**
- **정답지 구축 → 평가로 약점 발견 → 공식 문서로 개선 → 성능 향상**
- = **평가 기반 개발 루프(Evaluation-driven development)**
- 전부 **on-device**, **공식 근거 기반**, **팀 검증**

🎤 **대본**
"저희의 핵심은 평가를 한 번 하고 끝낸 게 아니라, 평가로 약점을 찾아 개선하는 루프를 갖췄다는 점입니다. 모두 로컬에서, 공식 근거로, 팀 검증을 거쳤습니다."

## 예상 질문 & 답변 (Q&A)

**Q. 정답(ground truth)은 어떻게 정했나요?**
A. 공식 문서(보건복지부 사업안내 등)를 근거로 정답을 지정하고, 한국어 팀원이 공식 자료와 대조해 검토·승인했습니다. JSONL 파일로 공개해 재현·검증이 가능합니다.

**Q. RAGAS 라이브러리를 썼나요?**
A. 아니요. 같은 4대 지표를 **로컬 LLM으로 자체 구현**했습니다. RAGAS는 기본적으로 외부 API가 필요한데, 저희는 on-device 원칙을 지키기 위해서입니다.

**Q. 심판(judge)을 답변 모델과 같은 걸 쓰면 공정한가요?**
A. 한계로 인정합니다. 그래서 검색은 키워드 매칭(객관적)으로, 생성만 LLM 심판으로 나눠 측정했고, 교차검증은 향후 과제로 두었습니다.

**Q. Hit@3 75%면 낮지 않나요?**
A. 초기 51%에서 개선한 수치이고, 핵심 복지(기초연금·정신건강 등)는 90% 이상입니다. 낮은 주제는 코퍼스 공백이 원인으로, 공식 문서 추가로 개선 경로까지 제시했습니다.

**Q. 왜 on-device(로컬 LLM)인가요?**
A. 어르신의 민감한 대화(건강·우울·위기)가 외부로 나가지 않도록 프라이버시를 보장하기 위해서입니다.

**Q. 이상신호 '위험'을 놓치면 위험하지 않나요?**
A. 그래서 위험 Recall을 가장 중요한 지표로 봤고, 규칙(키워드)만으로는 낮던 것을 LLM 심판을 더해 개선했습니다. 과잉 경보보다 미탐을 더 경계합니다.
